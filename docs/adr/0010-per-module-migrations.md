# 0010. Each module migrates its own schema with goose

- Status: Accepted
- Date: 2026-09-30

## Context

The ledger is the first module with tables, and every later module will add its own.
ADR 0001 makes a module's internals private to it; its tables are part of those
internals. The queries are generated by sqlc (ADR 0002), which must read the same schema
the migrations create.

Ledger tables refuse `DELETE` and `TRUNCATE` (ADR 0009), so tests cannot share one
database and clean it between runs.

## Decision

- Each module owns a PostgreSQL schema named after it (`ledger`) and keeps its migrations
  in `internal/<module>/migrations`, embedded in the binary. The module exports
  `Migrate`, which calls `postgres.Migrate` with its schema and files.
- `postgres.Migrate` runs goose with a version table inside the module's schema
  (`ledger.goose_db_version`) and a PostgreSQL session lock, so modules migrate
  independently and concurrent runs are safe.
- `jupiterctl migrate` applies every module's migrations; processes never migrate on
  startup.
- sqlc reads the migration files as its schema, and CI fails when generated code is
  stale (`make generate-check`).
- Integration tests start one PostgreSQL container per package, migrate a template
  database once, and give each test its own database cloned from it
  (`postgrestest.Server.Pool`).

## Alternatives rejected

- **One global migration sequence.** Every module's changes would interleave in one
  history, and nothing would stop one module's migration from touching another's tables.
- **golang-migrate or tern.** Either would work: both run plain SQL files, allow a custom
  version table and are read by sqlc. goose was preferred for its `Provider` API, which
  takes the files, the version store and the lock per call with no global state, and for
  Go-function migrations should a data migration ever need one.
- **Atlas.** Declarative schema management is powerful, but it is a second schema
  language and a larger tool than one module's migrations need.
- **Migrating on process start.** Several replicas starting at once would race, and a
  bad migration would take every process down with it.
- **Truncating between tests.** Impossible by design for ledger tables; cloning a
  template database takes milliseconds.

## Consequences

- Cross-module foreign keys are not possible, which is intended: modules refer to each
  other by identifier through their public interfaces.
- A deployment runs `jupiterctl migrate` before starting new binaries.

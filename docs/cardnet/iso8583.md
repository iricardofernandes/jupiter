# The card network's ISO 8583 specification

This is the message specification Jupiter's acquirer connector (`internal/acquirer`) and
the card network simulator (`internal/sim/cardnetwork`) both implement, in code, as
[`pkg/cardnet`](../../pkg/cardnet). It plays the part of the document a real network
publishes to its acquirers. Real schemes' specifications (Visa BASE I, Mastercard CIS, the
Brazilian ABECS and Elo manuals) are gated, so this one is built from public sources and
says, for every element, which:

- **Sourced**: taken from a public description of ISO 8583:1987 that the research read:
  [Wikipedia's ISO 8583 article](https://en.wikipedia.org/wiki/ISO_8583), the
  [LinkedIn write-up of the message flow](https://www.linkedin.com/pulse/whats-iso-8583-message-flow-part-two-ahmed-el-nazer),
  and the field formats of moov-io's `Spec87`, an open-source rendering of the 1987
  standard used in production ([research: card rails](../research/notes/04-card-rails.md)).
- **Unverified**: a meaning or code the research found only in background knowledge or
  secondary sources.
- **Jupiter's**: a convention of this network, where a real scheme would use proprietary
  fields that are not public.

## Framing and encoding

| | | |
|---|---|---|
| Transport | TCP, one long-lived connection per acquirer process | Jupiter's |
| Frame | a two-byte, big-endian binary length, then the message | Sourced (moov-io's `network.Binary2Bytes`, a common framing) |
| Version | ISO 8583:1987 (message types 0xxx) | Sourced |
| Encoding | ASCII for every element; the bitmap as 16 hexadecimal characters | Sourced (`Spec87ASCII`) |
| Bitmaps | a primary bitmap of 64 bits; bit 1 set means a secondary follows, for elements 65 to 128 | Sourced |

## Message types

| MTI | Meaning | Sent by | Answered with | |
|---|---|---|---|---|
| 0100 | Authorization request: hold the amount, capture later | acquirer | 0110 | Sourced |
| 0200 | Financial request. Processing code 000000 is a single-message purchase, authorized and completed at once; 200000 is a refund, a credit to the card | acquirer | 0210 | Sourced (types); refund use unverified |
| 0220 | Completion advice: the capture of an authorization, for up to its amount | acquirer | 0230 | Sourced (type); its use as the capture is unverified |
| 0221 | Completion advice, repeat | acquirer | 0230 | Sourced |
| 0400 | Reversal request: cancel an authorization, such as a void | acquirer | 0410 | Sourced |
| 0420 | Reversal advice: the acquirer cancels a request it cannot be sure did not happen, such as one it timed out | acquirer | 0430 | Sourced |
| 0421 | Reversal advice, repeat | acquirer | 0430 | Sourced |
| 0800 | Network management: sign-on, sign-off, echo | either | 0810 | Sourced |

A request (xx00) is answered or times out; the acquirer then reverses it. An advice (xx20)
must arrive: the acquirer repeats it (xx21) until the network acknowledges it. Both rules
are sourced from the message-flow write-up.

## Data elements

| DE | Name | Format | Used in | |
|---|---|---|---|---|
| 0 | Message type indicator | n 4 | all | Sourced |
| 1 | Bitmap | b 64, hex | all | Sourced |
| 2 | Primary account number | n..19, LLVAR | 0100, 0200 purchase | Sourced. Not sent on reversals, completions or refunds: DE 48 NT and DE 90 name the transaction instead (Jupiter's), which keeps card numbers out of the acquirer's store-and-forward queue |
| 3 | Processing code | n 6 | 0100, 0200 | Sourced; 000000 purchase and 200000 refund are unverified codes |
| 4 | Amount, transaction | n 12, minor units | all but 0800 | Sourced |
| 7 | Transmission date and time | n 10, MMDDhhmmss, UTC | all | Sourced |
| 11 | Systems trace audit number (STAN) | n 6 | all | Sourced. Every message has its own; the connection matches an answer to its request by it |
| 12 | Time, local transaction | n 6, hhmmss | 0100 | Sourced; local means the merchant's time zone, America/Sao_Paulo |
| 13 | Date, local transaction | n 4, MMDD | 0100 | Sourced |
| 14 | Date, expiration | n 4, YYMM | 0100, 0200 purchase | Sourced |
| 18 | Merchant type (MCC) | n 4 | 0100 | Sourced (element); 5999 for every merchant until merchants have their own is Jupiter's |
| 22 | Point of service entry mode | n 3 | 0100 | Sourced (element); 810 e-commerce and 102 credential on file are unverified codes |
| 32 | Acquiring institution identification code | n..11, LLVAR | all | Sourced |
| 37 | Retrieval reference number (RRN) | an 12 | all but 0800 | Sourced. Jupiter's are the last digit of the year, the day of the year and an 8-digit sequence; clearing records carry it |
| 38 | Authorization identification response | an 6 | 0110 | Sourced |
| 39 | Response code | an 2 | responses | Sourced; see below |
| 41 | Card acceptor terminal identification | ans 8 | 0100, 0200 | Sourced (element); JUPITER1 for card-not-present is Jupiter's |
| 42 | Card acceptor identification code | ans 15 | all but 0800 | Sourced (element); "M" and 14 hex characters of the SHA-256 of the merchant's id is Jupiter's |
| 48 | Additional data, private | ans..999, LLLVAR | see below | Sourced (element, private use by definition); its subfields are Jupiter's |
| 49 | Currency code, transaction | n 3, ISO 4217 | all but 0800 | Sourced; 986, the real, is the only currency |

| 90 | Original data elements | n 42 | 0220, 0400, 0420, 0421 | Sourced (element); the layout, original MTI (4), STAN (6), transmission date and time (10), acquiring institution (11) and forwarding institution (11), is unverified |

### DE 48 subfields

Tag (2 characters), length (2 digits), value. All are Jupiter's.

| Tag | Meaning | Sent in | Answered in |
|---|---|---|---|
| AV | 3-D Secure authentication value (CAVV/AAV), which the network checks | 0100 after authentication | |
| DS | 3-D Secure directory server transaction id | 0100 with AV | |
| EC | Electronic commerce indicator | 0100 with AV | |
| TC | Network token cryptogram, for DE 2 holding a network token | 0100 with a token | |
| CV | Card verification code | 0100, the first authorization of a card only | |
| IF | Installment financing: M merchant (parcelado lojista), I issuer (parcelado emissor) | 0100 with DE 67 | |
| NT | Network transaction identifier: on a merchant-initiated 0100, the one of the payment that stored the card; on 0200 refunds, 0220 and reversals, the one of the authorization | as said | 0110 |
| PA | Partial approval capable: 1. Jupiter never sends it | 0100 | |
| SC | Stored credential: I customer-initiated, storing the card; C customer-initiated, on a stored card; M merchant-initiated | 0100 | |
| SI | Approved by the network in stand-in, the issuer being unavailable: 1 | | 0110 |

The stored-credential rules follow the schemes' framework as the research described it,
unverified: a merchant-initiated payment must carry the network transaction id of the
customer-initiated one that stored the card.

## Network tokens

The network's token service is HTTP JSON on the same address as its files. All of it is
Jupiter's convention; real token services (VTS, MDES) are behind onboarding.

| | |
|---|---|
| `POST /v1/tokens` | `{token_requestor_id, pan, exp_month, exp_year}` → `{token_reference, token, exp_month, exp_year, status}`. The token is a card number of the network's range 489537 |
| `POST /v1/tokens/{reference}/cryptograms` | `{amount}` → `{cryptogram}`, good once, for that amount |
| Events | `POST` to the requestor: `{type: token.updated or token.suspended, token_reference, status, last4, exp_month, exp_year}`, signed in `Cardnet-Signature` as `t=unix,v1=hex HMAC-SHA256` of `t.body` |

An authorization with a token carries it in DE 2, its expiry in DE 14 and the cryptogram
in DE 48 TC; the network checks the cryptogram, swaps in the card, and the issuer never
sees the token.

## Clearing files

The network closes each business day by writing, for each acquirer, a file of the
completions and refunds it accepted that day, served at
`GET /v1/acquirers/{acquirer}/clearing/{YYYY-MM-DD}`. The format is Jupiter's; real
clearing (Visa BASE II, Mastercard IPM) is proprietary. One record per line, fixed
width, ASCII:

| Record | Layout |
|---|---|
| Header | `H`, business date (YYYYMMDD), acquirer (11) |
| Detail | `D`, kind (1: C completion, R refund), RRN (12), network transaction id (15), amount (12), currency (3), installments (2), authorization code (6), merchant (15) |
| Trailer | `T`, record count (6), completions total (15), refunds total (15) |

The reader checks the trailer against the records, so a truncated or altered file is
refused whole.
